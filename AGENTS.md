# Глобальные правила: Разработка плагинов Minecraft (Paper API)

## 1. Стек и сборка
- **Ядро:** Paper API 1.21+ (Java 21).
- **Сборщик:** Maven (`pom.xml`).
- **Проверка сборки:** После написания или изменения Java-классов всегда проверяй компиляцию командой `mvn test-compile` или `mvn compile`.

## 2. Стандарты кода
1. **Никакого Legacy ChatColor:** Всегда используй `net.kyori.adventure.text.Component` и `MiniMessage` для форматирования текста, лора предметов и сообщений.
2. **Paper API приоритетнее Spigot/Bukkit:** Используй `PersistentDataContainer` (PDC) для кастомных тегов на предметах и мобах, современные эвенты Paper и `paper-plugin.yml` / `plugin.yml`.
3. **Потокобезопасность и TPS:** Никогда не выполняй сетевые запросы, работу с БД или тяжелые операции с файлами в основном потоке сервера (Main Thread). Используй асинхронные задачи `BukkitScheduler` или `CompletableFuture`.
4. **Управление памятью:** Не храни прямые ссылки на объекты `Player` или `Entity` в долгоживущих коллекциях (`Map`, `List`) — храни их `UUID` и очищай данные при `PlayerQuitEvent`.

## 3. Политика хранения данных (SQLite вместо YAML)
1. **Никаких YAML для данных и объектов:** Запрещено сохранять прогресс игроков, статистику, стадии квестов, валюту или координаты созданных в мире объектов (вышек, построек и т.д.) в файлы `player.yml`, `models.yml` или любые другие текстовые файлы. YAML разрешен **только** для статических настроек плагина в `config.yml`.
2. **Обязательное использование SQLite:**
   - Все динамические данные игроков и расставленные в мире сущности/модели должны храниться в базе данных **SQLite** (`database.db`) с включенным режимом `PRAGMA journal_mode=WAL;`.
   - Использовать встроенный драйвер Paper (`jdbc:sqlite:`).
   - Всегда проектировать архитектуру с кэшированием в оперативной памяти (`ConcurrentHashMap`), асинхронной загрузкой при входе игрока и фоновым сохранением через `CompletableFuture`, чтобы полностью исключить лаги основного потока сервера (Main Thread).

## 4. Правила работы с Git
1. **Инициализация и `.gitignore`:**
   - Перед началом работы проверяй наличие репозитория через `git status`. Если Git не инициализирован — выполни `git init -b main`.
   - До первого `git add` обязательно проверь наличие и актуальность `.gitignore`. В нем должны быть исключены: `target/`, `*.jar`, `.idea/`, `*.iml`, `.vscode/`, `.env`, `*.db`, `*.db-wal`, `*.db-shm`.
   - При подключении удаленного репозитория проверяй `git remote -v`, добавляй `origin` (`git remote add origin <url>`) и при первом пуше связывай ветку (`git push -u origin main`).
2. **Ветвление и синхронизация:**
   - Перед реализацией новых механик или рефакторингом проверяй текущую ветку (`git branch --show-current`). Если не указано работать напрямую в `main`, создавай тематическую ветку: `git switch -c feat/<name>`, `git switch -c fix/<name>` или `git switch -c refactor/<name>`.
   - Перед началом новой задачи в существующем репозитории подтягивай актуальные изменения: `git pull --rebase origin main`.
3. **Коммиты и релизы:**
   - Перед каждым коммитом проверяй `git status` и `git diff`, чтобы исключить попадание в индекс скомпилированных артефактов, тестовых БД и секретов.
   - Делай атомарные коммиты (одна логическая задача — один коммит) **строго после успешного прохождения** `mvn test-compile` или `mvn compile`.
   - Формат коммитов — **Conventional Commits**: `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `ci:` (при необходимости со scope, например `feat(db): ...`).
   - Для выпуска релизов (включая триггеры CI/CD) используй аннотированные SemVer-теги: `git tag -a vX.Y.Z -m "Release vX.Y.Z"` и `git push origin vX.Y.Z`.
4. **Безопасность и ограничения:**
   - Для безопасной отмены последнего локального коммита с сохранением изменений используй `git reset --soft HEAD~1`, для отмены уже запушенного коммита — только `git revert <hash>`.
   - **Строго запрещено без явного подтверждения пользователя:** `git push --force`, `git reset --hard`, `git clean -fd`, принудительное удаление веток (`git branch -D`) и автоматический `git push` после коммита, если пользователь не просил отправлять изменения в remote.
